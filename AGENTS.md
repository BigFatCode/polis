# Working on POLIS

## Start here

Read [current direction](docs/direction.md) before planning or changing product behavior. Follow its links for unresolved decisions relevant to the task.

## Load context when needed

- **Domain language:** consult [CONTEXT.md](CONTEXT.md) when naming concepts or discussing their relationships. Keep it a glossary.
- **Ideas or experiments:** consult the [idea index](docs/ideas/README.md) before proposing scope, choosing a delivery platform, or splitting domains. Follow relevant idea records and their reconsideration triggers.
- **Knowledge changes:** follow [docs/knowledge.md](docs/knowledge.md) when creating or editing project documentation, recording decisions, or using Wayfinder. It defines document ownership and the local tracker convention.
- **Architecture:** read relevant ADRs under `docs/adr/` if that directory exists. Create an ADR when a significant decision is actually made.
- **Prototype work:** read the [CLI experiment status](sandbox/cli-prototype/README.md) before using its code or instructions as a starting point.
- **Fiction:** read the [lore](docs/POLIS-lore-document.md) for narrative work.
- **Historical intent:** use the [earlier game design](docs/POLIS-design-document.md) and [earlier overview](docs/archive/README-v0.02.md) when tracing an idea's origin.

## Preserve distinctions

Keep confirmed direction, proposed ideas, decisions, fiction, and observed implementation behavior distinguishable. When sources conflict, expose the unresolved choice and ask the owner; a newer filename or working prototype does not settle product intent.

Maintain one authoritative home for each fact or decision and link from other documents. When promoting an idea, update its status and link the resulting decision or experiment so its history remains traceable.
